Field assessment · NVIDIA OpenShell 0.1.9 · Windows 10 + WSL 2 + Docker Desktop · 23 Nov 2026

The boundary held every time. Most of what's around it needs work.

An assessment from one day of hands-on use: a .NET agent on local Nemotron, two policy decisions, an exfiltration attempt, a red-team scan. Each finding is marked observed (we hit it), docs (documented behaviour) or inferred (reasoned, not tested).

Isolation and enforcementStrong
Every unlisted file, host and binary was blocked, including a real exfiltration attempt.
Policy modelStrong
Rules bind a binary to a host and port. Precise, readable, hot-reloadable.
Human reviewMixed
The proposal loop works, but proposals carry little context and the prover only reasons about credentials.
Developer experienceMixed
Opaque admission errors, one upload corruption, no runtime presets.

Experimental. Sandboxes fail until you find one undocumented-for-WSL setting.
Stability and docsWeak
Breaking removals between minor versions; old doc pages answer "Page Not Found".

What held up

Before the problems: the core idea works, and some details are better than in most agent sandboxes.

Policy outside the agentThe model obeyed an instruction to post source code to an attacker's host. The sandbox refused the DNS lookup and the connection anyway.
Binary-level identityThe same host was allowed for curl and denied for dotnet. Rules name the kernel-resolved binary, not a process name.
Deny, propose, approveA denial becomes a reviewable rule with binary, host, port and a rationale, and an approval applies without restarting the agent.
An audit trail by defaultEvery decision is an OCSF event; rule history reads like a change log.
Errors that teach, sometimesThe binary denial included a "SYMLINK HINT" explaining that /usr/bin/dotnet resolves to /usr/share/dotnet/dotnet.
A prover in the loopIt flagged that approving dotnet → the model endpoint widened credential reach, before anyone clicked approve.

The approval race (I6)

Measured from the sandbox logs. Both waits come from polling: the supervisor flushes its denial analysis, and later picks up the new policy, on its own schedule.

A person approves, retries straight away, and is denied again. Scripts and CI hit this every time. Fix: rule approve --wait that returns once the sandbox has acknowledged the new policy revision, plus push-based reload.

The prover gap (I8)

The prover checked both proposals. It warned on the harmless one and stayed silent on the leak.

allow_host_openshell_internal_11434prover: credential_reach_expansion
dotnet → the local model. No credentials involved (Ollama). Approved.
allow_collector_evil_example_443prover: no new findings
dotnet → an unknown external host, right after the agent read source code and in the middle of a POST. Rejected by a person.
Proposed: a data-egress check next to credential reach. Flag a rule when it adds a destination outside the organisation's known domains and the same process has read workspace files, or sends a large or high-entropy body. Add domain signals (first seen, newly registered, reserved TLD, paste and file-drop services) to the rationale a reviewer sees.

What the boundary sees, and what it can't

OpenShell governs where an agent can go and what it can touch. It does not judge what the agent says, or what it sends through a door that is already open.

Inside its view

  • Files the process opens (Landlock): /app was unreadable until moved
  • Every new host and port, per binary: dotnet to the model, to an attacker
  • Processes and privileges (seccomp, non-root identity)
  • Credentials: placeholders resolved only at approved endpoints (documented; not tested here)

Outside its view

  • What the model says: AgentEval's red-team got "PWNED" out of it 2 times in 3, and OpenShell had nothing to block
  • Data inside allowed traffic: a prompt to the inference endpoint, or a commit to an approved Git host, can carry secrets (inferred)
  • Intent: a proposal shows binary and host, not the tool call or the payload behind it
  • The host machine itself when the agent runs outside a sandbox: one v1 run sent code out from the host

The answer to the right column is layering: evaluation and red-teaming for model behaviour (AgentEval), content checks on allowed egress (OpenShell's supervisor middleware is the documented extension point), and traces that tie a network request to the tool call that made it.

How I would improve it

Now: remove the paper cuts

  1. Detect Docker Desktop and default to bridge mode; make doctor test a real supervisor callback (I1).
  2. Checksum every upload and fail loudly (I11).
  3. rule approve --wait and push-based reload (I6).
  4. Ship runtime presets (dotnet, node, java, python venvs) and profile lint --image (I4, I5).
  5. An image check preflight with fix-it messages (I3).
  6. Tombstone messages for removed commands, and real redirects for old docs (I13).

Next: make review meaningful

  1. Give proposals context: method, path, body size, the trace and span that made the call, the last tool call (I7).
  2. A data-egress risk class in the prover (I8).
  3. Turn filesystem denials into proposals too, not only network ones (I3).
  4. rule promote to move an approved rule into a profile or policy file, with a diff (I9).

Later: cover the open doors

  1. Content checks on allowed egress through default supervisor middleware: secrets, source code, size and rate anomalies (I14).
  2. Accept evaluation and guardrail signals as policy inputs, so a red-team failure can tighten a rule (I15).
  3. Show Landlock ABI and enforcement level in status, with a fail-closed option (I2).

Scope of this assessment: one machine, one day, OpenShell 0.1.9 on an experimental platform, a local credential-free model. The hosted-credential path (placeholder injection) was prepared but not run, and allowed-channel exfiltration (I14) is reasoned, not tested. Several findings may already be addressed on Linux or in newer releases.
